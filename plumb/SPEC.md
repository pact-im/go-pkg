# plumb specification

plumb is a command-line code generator for Go. It reads a set of Go packages, finds
declarations tagged with a `//plumb:<name>` directive (“providers”), and generates a
function that calls them in dependency order: the *injector*. Unlike hand-written
dependency injection, and unlike [wire], you do not write the injector or declare its
signature: plumb infers both from the providers.

This document is the behavioral specification for plumb. It is written so that an
implementer can build plumb from scratch, in any language targeting Go source output,
without seeing the reference implementation. It describes **what plumb does** and the
**edge cases** it must handle; it says nothing about how the reference implementation is
structured (you are expected to design your own architecture; see [§8](#8-implementation-and-testing-guidance)).

## The model in one minute

- A **provider** is a Go declaration that produces a value, tagged with a line comment
  `//plumb:<name>`. Functions, methods, package-level variables and constants, conversions,
  struct fields, and struct types can all be providers.
- A **set** is every provider sharing one `<name>`, gathered across all scanned packages.
  plumb emits one function per set, named `<name>`.
- plumb wires **by type**: within a set, each Go type has **at most one value**. A
  provider’s parameters are the types it *consumes*; its results are the types it
  *produces*. A type produced by one provider and consumed by another is wired
  automatically.
- The injector’s **signature is inferred**: its parameters are the types that some
  provider needs but none produces (*inputs*); its results are the types that some
  provider produces but none consumes (*outputs*), plus an aggregated cleanup and/or a
  trailing error when the providers call for them.

A minimal example. Given, in package `example.com/app`:

```go
type Config struct{ Addr string }
type Server struct{}

//plumb:build
func NewConfig() *Config { return &Config{Addr: ":8080"} }

//plumb:build
func NewServer(c *Config) (*Server, error) { return &Server{}, nil }
```

plumb generates a function equivalent to:

```go
// Code generated by plumb. DO NOT EDIT.

package app

func build() (server *Server, err error) {
	config := NewConfig()
	server2, e := NewServer(config)
	if e != nil {
		err = e
		return
	}
	server = server2
	return
}
```

No type is an input here (every parameter is produced internally), so `build` takes no
arguments; `*Server` and `error` are the outputs.

## The central invariant

> **Valid input produces compilable output.**

If the scanned packages type-check and their providers are self-consistent, plumb’s output must
be valid, compilable Go, across both same-package and separate-package generation (see
[§6](#6-packaging-qualification-and-output-safety)). When the input is *not*
self-consistent (an ambiguous producer, a dependency cycle, an unsupported construct),
plumb must fail with a clear, located diagnostic rather than emit broken code. plumb must
never silently emit code that fails to compile.

Two corollaries an implementer must honor:

- **Determinism.** For the same input, plumb produces byte-for-byte identical output,
  regardless of the order in which packages and files happen to be read. Output ordering
  is anchored to source position, not to filesystem or loader iteration order.
- **Idempotent regeneration.** Re-running plumb over its own previous output is safe and
  reproduces (or correctly updates) that output. See [§6](#6-packaging-qualification-and-output-safety).

Note the asymmetry: the guarantee binds plumb only on **valid input**. On input that does
not type-check, plumb is best-effort: it must not crash, but its output may carry the
user’s own type error (see [§6](#regeneration) on tolerated load errors, and
[§5](#constraint-near-misses)).

The guarantee is also relative to the **build context** at generation time: packages load
under the active environment (`GOFLAGS=-tags=… plumb .` scans tag-gated files; there is
no tags flag of plumb’s own), so wiring that references a tag-gated provider compiles
exactly where that tag is set. Generating under a tag and building without it is a
misconfiguration the compiler reports, not plumb.

## Scope

plumb **does**: discover providers, infer the injector signature, order providers by
dependency, bridge value/pointer mismatches, instantiate generics on demand, aggregate
cleanups and errors, and write a gofmt-canonical generated file.

plumb **does not**: run the providers, resolve dependencies at runtime, perform any
reflection, match interfaces structurally (matching is by *exact* type; see
[§3](#3-provider-kinds)), or support more than one value of a given type per set (see
[§4](#wiring-by-type)).

Throughout, generated-code listings are *examples of conforming output*. The exact local
variable names and import aliases are an implementation choice; the **semantics** they
illustrate (ordering, error handling, teardown order, coercion) are required.

# 1. Command-line interface

## Synopsis

```
plumb [-package-name=<name>] [-import-path=<path>] [-output=<file>] [-v] [<packagePattern>...]
```

plumb scans the matched packages, finds every set across all of them, and writes one file
containing one function per set.

## Package patterns

Zero or more patterns in the style the Go toolchain’s package loader accepts: `.`,
`./service`, `./...`, or a full import path. A single pattern may match several packages,
and several patterns may be given. With **no** pattern, plumb scans the current directory
(`.`).

The scanned packages are loaded with full type information. plumb reads each package’s
syntax (to find directives in comments) and types (to resolve provider and signature
types). It does **not** need, and should not pull in, the source of imported
dependencies: types from imported packages resolve from their compiled/export form. (An
implementation that can avoid type-checking the whole transitive dependency graph should:
it is the bulk of load time and plumb does not need it.)

## Flags

### `-package-name=<name>`

The identifier emitted in the generated `package <name>` clause. It must be a valid Go
identifier and not the blank identifier `_`.

Default: the name of the package the generated file belongs to (the destination), when
that package is one of the scanned packages. When the destination is **not** scanned (a
separate package; see [§6](#6-packaging-qualification-and-output-safety)), there is no
name to infer and `-package-name` is **required**.

When the destination **is** scanned, its real package name is known, so an explicit
`-package-name` that **differs** from it is rejected: the generated file must share the
destination’s `package` clause, and honoring a conflicting value would emit an
uncompilable one. A value equal to the inferred name is accepted (merely redundant).

### `-import-path=<path>`

The import path of the package the generated file belongs to (the *destination*). This
(not where the file is written) determines what is referenced unqualified and what is
imported and qualified (see [§6](#6-packaging-qualification-and-output-safety)).

It must be a **valid Go import path**: non-empty, and accepted by the same rule the Go
toolchain applies to import paths. A malformed path (for example one containing a space)
is rejected with a clear error.

Default and rules:

- Omitted, with exactly **one** scanned package → that package’s import path. (So a
  single-package `go:generate` needs no flags.)
- Omitted, with **more than one** scanned package → ambiguous; plumb must error and
  require `-import-path`.
- A path matching **one** scanned package → same-package generation into that package.
- A path matching **no** scanned package → a separate package (everything qualified);
  `-package-name` is then also required.

It is an error to infer an import path from file arguments that resolve to no real import
path (e.g. a synthetic `command-line-arguments` package); require `-import-path` in that
case.

### `-output=<file>`

The file to write. Default: standard output. plumb does not create intermediate
directories; the parent directory must already exist.

The output path additionally identifies, by **base name**, the file plumb is overwriting,
which matters for same-package collision handling and regeneration
(see [§6](#6-packaging-qualification-and-output-safety)). When writing to standard output,
no file is identified as “the one being overwritten.”

### `-v`

Print a discovery-and-inference report to standard error (the generated code still goes to
`-output`/stdout). The report is for humans diagnosing what plumb saw and inferred; its
exact layout is not contractual, but it should include:

- the packages scanned, and the destination package being generated into;
- per set: the set name, and each provider with its kind and the types it consumes and
  produces;
- the **inferred injector signature** for the set (inputs → outputs);
- the imports the generated file will use.

Illustrative shape (not a required format):

```
plumb: scanned 1 package(s): example.com/app
plumb: generating into package "example.com/app"

set "build" (2 providers):
  call NewConfig in() → out(val *Config, cleanup func() error)
  call NewServer in(*Config) → out(val *Server, err error)
  inject build in() → out(val *Server, cleanup func() error, err error)
  imports:
    "errors"
```

The report, like the generated source, must be **deterministic**: byte-identical across
read orders. The determinism guarantee covers exactly these two: the generated source and
the `-v` report. It does **not** extend to the tolerated-load-error notes surfaced
alongside the report (see “Exit behavior” and [§6](#regeneration)), which follow the order
the loader encountered the errors; they are a diagnostic aid, not part of the contract’s
reproducible surface. Because an unprovided type silently becomes an input (it is *not* an
error; see [§4](#signature-inference)), `-v` is the primary way a user notices a typo or a
forgotten provider that widened the signature.

## Exit behavior

- On success: write the generated source to `-output` (or stdout) and exit 0.
- On failure: write a diagnostic to standard error, prefixed so it is clearly plumb’s
  (e.g. `plumb: <message>`), and exit non-zero. Nothing is written to the output file.
- When generation fails and the load tolerated type errors (see [§6](#regeneration)),
  those tolerated errors are also surfaced, so a genuine provider type problem is not
  swallowed behind a downstream diagnostic.

All diagnostics that the configured streams receive must go through those streams, not
directly to the process’s standard error, so the behavior is testable.

## go:generate

The intended way to wire plumb into a project is a `go:generate` directive in the
providers’ package, which infers both the package name and the import path from where it
sits:

```go
//go:generate plumb -output=plumb_gen.go
```

Commit the generated file, and re-run plumb when providers change.

# 2. Directives and sets

## Grammar

A provider is tagged with a Go **line directive**: a `//`-comment whose text begins
immediately with `plumb:` (no space), followed by the set name.

```go
//plumb:build
```

A conforming implementation recognizes directives by the **same rule gofmt applies** (the
Go standard library exposes this as `go/ast.ParseDirective`). The rules that make a comment
a real Go *directive* rather than an ordinary comment:

- It is a `//` line comment, **not** a `/* */` block comment.
- There is **no space** between `//` and `plumb`. `// plumb:build` (with a space) is an
  ordinary comment and is **not** a directive. This matters because `gofmt` inserts that
  space into any `//`-comment that does *not* look like a known directive, so a malformed
  directive is silently demoted to a comment on the next format.
- The tool token is exactly `plumb`, followed by `:` and the name.

### The set name

The text after `plumb:` is the set name. It becomes the generated function’s name
verbatim, so:

- It must be a valid Go identifier (and not blank `_`).
- It should start with a **lowercase** letter. An uppercase first letter (`//plumb:Build`)
  is *not recognized by gofmt as a directive*, so gofmt rewrites it to `// plumb:Build`,
  silently disabling it. Treat a non-lowercase-initial name as the same trap the user
  must avoid. (If an exported wiring function is wanted, the user calls the generated
  unexported function from a small hand-written exported wrapper.)
- The directive takes **only** the set name: no arguments. `//plumb:build extra` carries a
  trailing argument and is rejected (see “Malformed directives”).
- Reserved-identifier interactions (`init`, `main`, predeclared names) are covered in
  [§7](#reserved-and-colliding-names).

### Malformed directives

Three cases, by how the comment relates to the directive grammar:

- **Not recognized as a directive at all → silently ignored.** A `//`-comment that does
  not match Go’s directive form is an ordinary comment and contributes no provider, with no
  error. This covers a space after `//` (`// plumb:build`), an empty name (`//plumb:`), and
  (importantly) a name that does not begin with a lowercase letter or digit, the
  gofmt-demotion trap: `//plumb:Build` is **not** a recognized directive, so the provider is
  **silently dropped**. This is the capitalization footgun the user must avoid.
- **Recognized as a `plumb:` directive but the name is not a valid Go identifier → an
  error.** When the comment *is* a directive whose tool is `plumb` but whose name fails the
  Go-identifier rule (for example `//plumb:123`, a digit-initial name that is recognized as
  a directive yet is not an identifier), plumb reports an error and generation fails.
- **Recognized as a `plumb:` directive but carrying arguments → an error.** A plumb set
  directive names a set and nothing else; trailing text (`//plumb:build extra`) is rejected
  rather than silently treated as set `build`.

Because plumb’s model is “an unprovided type silently becomes an input,” the *silent* case
is the dangerous one: a mistyped or mis-capitalized directive widens the signature or
yields a confusing “no directives found.” A from-scratch implementation **may** additionally
warn when a comment looks like it was meant to be a `plumb` directive but was not recognized;
this is an optional quality-of-life improvement, not required behavior.

## What can be tagged

A directive attaches to the declaration it precedes (for a struct field or interface
method, the field/method it precedes). Test files are never scanned, so a directive in a
`_test.go` file is ignored: a deliberate limitation, and the one exception to the rule
that a recognized directive is never silently dropped (see
[§7](#directives-in-test-files-a-known-limitation)). The supported targets are:

- a package-level **function** (`//plumb:` on the `func` declaration);
- a **method** (directive on the method declaration; for an interface method, on the
  method element inside the interface type);
- a package-level **variable** (a value provider, or, for a blank variable with an
  explicit target type, a conversion);
- a package-level **constant** (must be typed);
- a **struct field** (directive on the field inside the struct type);
- a **struct type** (directive on the `type` declaration).

Each target’s semantics are specified in [§3](#3-provider-kinds).

**Locals are never providers.** Directives are only meaningful on the package-level and
type-member targets above. A `//plumb:` directive inside a function body (for instance on
a function-local declaration) is not silently ignored: no provider can attach there, so it
is rejected as a directive in an unsupported position (see
[§7](#directive-and-provider-validity)).

Two placements that *look* taggable but are **rejected** (see [§7](#directive-and-provider-validity)):

- an **embedded** struct field (give the field a name to use it);
- an **embedded** interface (declare the directive on a method instead).

### Multiple names in one declaration

A `var`/`const` spec may declare several names; the directive applies to the **spec**, so
every name it declares becomes a provider:

```go
//plumb:build
var A, B int   // both A and B are value providers of type int
```

Two providers of the same type (here both `int`) in one set are an **ambiguous producer**
error (see [§7](#set-resolution)), exactly as if two separate providers produced `int`.
Likewise, a struct-field directive declaring several names (`Foo, Bar Baz`) yields one
provider per name. A blank name mixed with named ones, in a `var`/`const` spec or a field
group (`A, _ int`), is skipped, so only the named entries become providers; a *wholly*
blank group declares nothing and is rejected (see [§7](#directive-and-provider-validity)).

### Group and spec directives

A directive before the `var`/`const`/`type` keyword attaches to the whole declaration, so
in a parenthesized block it applies to **every** spec in the block. It is **unioned** with
each spec’s own directives, not shadowed by them: a spec that names an extra set still joins
the block’s set too.

```go
//plumb:build
var (
	//plumb:test
	X = A{}   // joins build (from the block) and test (its own)
	Y = B{}   // joins build only
)
```

Naming the **same** set at both levels is a duplicate (the block already joins the spec to
it) and is rejected as a duplicate-directive error (see [§7](#set-resolution)), pointing at
the redundant spec directive. This is the same rule as repeating a directive on one
declaration, applied across the block/spec boundary.

## Sets

- A **set** is the union of all providers carrying a directive with the same name, across
  **all** scanned packages. Providers for one set may live in different packages
  (see [§6](#multiple-packages)).
- plumb emits **one function per set**, named after the set.
- A single declaration may carry **several** directives to join several sets:

  ```go
  //plumb:build
  //plumb:test
  func NewClock() Clock { return realClock{} }
  ```

  Here `NewClock` is a provider in both `build` and `test`, and appears in both generated
  functions. A declaration joins a set at most once: repeating the *same* name on one
  declaration (`//plumb:build` twice) is rejected as a duplicate-directive error, naming the
  set and pointing at the redundant directive to remove.
- If the scan finds **no** directives at all, plumb fails (there is nothing to generate).

# 3. Provider kinds

Every provider, whatever its kind, reduces to the same abstraction: a set of **input
types** it consumes and a set of **output types** it produces, plus a rule for rendering
the call that produces the outputs from the inputs. This section gives each kind’s inputs,
outputs, and an equivalent function form. The wiring rules that combine providers are in
[§4](#4-the-generated-injector).

Two cross-cutting rules apply to every kind:

- **Matching is by exact type.** A consumer of `io.Reader` is satisfied only by a producer
  of `io.Reader`, never by a producer of a concrete type that implements it. To bridge
  between types that are not identical, use a conversion (below). The one automatic bridge
  plumb performs is value⇄pointer of a named, type-parameter, or basic type (see
  [§4](#value-and-pointer)).
- **Cross-package export.** When the generated file lives in a different package from a
  provider (separate-package mode, see [§6](#6-packaging-qualification-and-output-safety)),
  every symbol and type the generated code must name across that boundary has to be
  exported. An unexported provider, signature type, or type argument that cannot be named
  from the destination is an error.

## Function providers

The common case: a constructor. Parameters are inputs; results are outputs.

```go
//plumb:build
func NewStore(db *sql.DB) (*Store, error) { ... }
```

Inputs: `*sql.DB`. Outputs: `*Store` (a value), and a trailing `error` that makes the
whole injector fallible (see [§4](#errors)). A result of the bare type `func()` is a
**cleanup**, and an `error` result is the error channel; both are special (see
[§4](#cleanup)) and are not ordinary values.

**Variadic** parameters are supported: a variadic parameter is a dependency of its slice
type (`[]T`), and the generated call forwards that slice with `...`.

### Side-effect providers

A function or method with **no results at all** is a **side-effect provider**. It consumes
its inputs and is emitted as a bare call (`Register(mux, h)`), assigned to nothing, whose
purpose is the effect itself: registering a handler, warming a cache, publishing a metric.

Because it produces nothing, a side-effect provider is **determinate**: like any provider
that needs no consumer to pin it, it is always instantiated, so its call always appears in
the injector body. It is ordered after the providers of its inputs, and since it has no
output, nothing depends on it in turn. It contributes no value output and none of the
special result shapes: a side-effect provider has no `error` channel (it never makes the
injector fallible) and no `func()` cleanup, because both of those *are* results: a
provider whose only result is a cleanup or an error has one result, not zero, and is an
ordinary provider (see [§4](#cleanup)), not a side-effect one.

Two consequences worth stating. A **dropped return type** turns a constructor into a
side-effect provider silently: `func NewDB(cfg *Config)` written for `func NewDB(cfg
*Config) *DB` leaves `*DB` produced by nobody, so every consumer of `*DB` gains it as an
injector input (the “unprovided means input” non-error of [§4](#signature-inference)) and
the `NewDB` call runs only for its effect. `-v` shows the widened signature, which is how
the mistake is caught. And a **generic** side-effect provider (free type parameters
appearing only in its inputs) is an anchor ([§5](#free-unpinned-type-parameters)):
instantiated unconditionally, with those parameters lifted onto the injector header. A set
named `init` or `main` composed of side-effect providers generates the corresponding
`func init()` / `func main()` (see [§7](#reserved-and-colliding-names)).

## Method providers

A method is a provider whose **receiver is its first input**. The generated code calls the
method on the receiver value, so the method name is never package-qualified, but the
method must be exported when the generated file is in a different package. A method whose
**receiver type does not resolve** (a typo’d or undefined receiver in input that does not
type-check) is rejected with a located type-does-not-type-check error, not a crash (see
[§7](#directive-and-provider-validity)).

```go
//plumb:build
func (db *DB) Store() *Store { return ... }
// equivalent to: func store(db *DB) *Store { return db.Store() }
```

For an interface method, the directive goes on the method element inside the interface
type; the interface is the receiver (input) and the method’s result is the output.

```go
type Reporter interface {
	//plumb:build
	Report() *Summary
}
// requires a Reporter, provides a *Summary; emitted as reporter.Report()
```

Methods on **generic** receivers are supported (see [§5](#generic-methods-fields-and-interfaces)).

## Variable providers

A package-level variable is a value provider, equivalent to a function returning it. The
generated code references the variable directly. The func()/error result special-casing
(see [§4](#cleanup)) applies only to function and method results, so a variable of type
func() is an ordinary value, not a cleanup, as is a field or conversion of that type.

```go
//plumb:build
var Stdin = os.Stdin
// equivalent to: func stdin() *os.File { return os.Stdin }
```

If a consumer needs a pointer to the variable’s type, plumb converts the value (see
[§4](#value-and-pointer)); the pointer is to a fresh copy, never to the variable’s own
storage.

## Constant providers

A package-level constant with an **explicit type** is a value provider, like a variable.

```go
//plumb:build
const DefaultPort Port = 8080   // provides Port
```

An **untyped** constant (`const DefaultPort = 8080`) has no determinate provided type and
is **rejected**. The constant must carry an explicit type.

## Conversions

A blank variable with an explicit target type is a **conversion provider**: it **consumes
the source type** and **produces the target type**, emitting the Go conversion `T(src)`.
The value on the right-hand side is only a type hint: the idiom `(*T)(nil)` means “the
source type is `*T`”. Binding a concrete type to an interface (the analog of wire’s
`wire.Bind`) is the common case, but it is not special: *any* conversion that the
blank-variable assignment type-checks is allowed (other than an identity conversion; see
below), because Go makes “assignable to `T`” a conversion rule.

```go
//plumb:build
var _ io.Reader = (*os.File)(nil)
// consumes *os.File, produces io.Reader; emitted as a conversion: reader := io.Reader(file)

//plumb:build
var _ chan<- struct{} = (chan struct{})(nil)
// consumes chan struct{}, produces chan<- struct{}; emitted as: send := chan<- struct{}(ch)
```

So the target may be an interface a source implements, a directional channel, a pointer
with an identical base, a named/underlying pair, and so on. The right-hand side must name a
determinate **source type**: a bare untyped `nil` (`var _ io.Reader = nil`) names no source
type and is **rejected**. Write `(*T)(nil)`.

An **identity conversion**, whose source type is identical to its target, is also
**rejected**: it consumes and produces the same type, a self-referential no-op. Because a
type alias is its target (see [§4](#wiring-by-type)), a conversion between an alias and the
type it names is an identity conversion too. There is nothing to bridge.

The generated conversion **parenthesizes the target type** exactly when Go would otherwise
mis-parse `T(x)`. Two ways it mis-parses: a **leading operator**, a pointer (`(*T)(x)`, else
read as a dereference) or a receive-only channel (`(<-chan T)(x)`, else a receive); and a
target whose rendered form **ends in a result-less `func`** (`(func())(x)`, else the trailing
`(x)` is read as the func’s result list). The trailing-func case reaches through composite
tails, so a slice, array, map, or channel of a result-less func, and a func whose sole result
is one, all need parentheses too: `([]func())(x)`, `(chan func())(x)`, `(map[K]func())(x)`,
`(func() func())(x)`, and nested forms like `([]chan func())(x)`. Every other target needs
none: named types, interfaces, structs, send-only channels, and composites not ending in a
bare func, including a func type *with* a result (`io.Reader(x)`, `map[string]func() int(x)`,
`[]int(x)`, `func() int(x)`).

## Struct field providers

A directive on a **field** makes that field a provider: it consumes the struct and
produces the field’s type.

```go
type Config struct {
	//plumb:build
	Port int
}
// equivalent to: func port(c *Config) int { return c.Port }
```

plumb consumes the struct as a **value or a pointer**, whichever the set already uses
elsewhere: it prefers `*Config` if some other provider produces or consumes `*Config`,
otherwise it takes `Config` by value. Field access reads identically for both forms. The
field need not be exported when the generated code is in the same package; cross-package,
it must be exported.

A field on a **generic** struct is a template (see [§5](#generic-methods-fields-and-interfaces)).
An **embedded** field cannot carry a provider directive; give the field a name.

## Struct type providers

A directive on a **struct type** makes the type build itself from the set. Its **exported
fields become inputs**, as if they were constructor arguments; **unexported fields are left
zero**. It produces the struct value.

```go
//plumb:build
type Server struct {
	Addr string      // exported → input
	DB   *DB         // exported → input
	log  *log.Logger // unexported → left zero
}
// equivalent to: func newServer(addr string, db *DB) Server { return Server{Addr: addr, DB: db} }
```

It provides the value `Server`. If another provider in the set needs `*Server`, plumb also
makes the pointer form available (it builds the value once and converts it; see
[§4](#value-and-pointer)), so the user may consume either `Server` or `*Server`. A
**generic** struct type works too, instantiated like any other generic provider.

A directive on a non-struct type (a defined non-struct type, an interface, or a type
**alias** whose target is not a struct) is **rejected**: struct-type providers are only
supported on struct types.

## Cleanup and error results

Three function/method result shapes are special and are **not** ordinary value outputs:

- a result of the **bare** type `func()` (no params, no results), a cleanup hook;
- a result of type `func() error`, a failable cleanup hook;
- a result of the predeclared `error` type, the provider’s failure channel.

Their semantics (aggregation, teardown order, error propagation) are in
[§4](#cleanup). Only the *bare* `func()`/`func() error` shapes are special: a **named**
function type (`type Handler func()`) is an ordinary value, so to wire a `func()` into the
bag as a value, give it a defined name.

A provider that returns **two values of the same type**, or **more than one `error`**, is
rejected (see [§7](#set-resolution)).

# 4. The generated injector

For each set, plumb generates one function. This section specifies how its signature is
inferred, how providers are ordered, and how values, errors, and cleanups flow through it.

## Wiring by type

Within a set, plumb tracks **one value per Go type**. A provider’s inputs are demands for
types; its outputs are supplies of types. A type supplied by one provider satisfies every
demand for that exact type.

Two rules follow, and both are load-bearing:

- **One value per type.** Two parameters of the same type always receive the *same* value.
  You cannot wire two distinct values of one type in a set. (To model several values of an
  underlying type, the user introduces distinct defined types, or uses a slice/array; see
  “Not supported” at the end.)
- **One producer per type.** If two providers in a set both produce the same type, that is
  an **ambiguity error**, including a single provider that returns two values of the same
  type. plumb never picks a winner.

Type identity is Go’s type identity (what `go/types` calls *identical*), including type
arguments of generic instantiations and the way a type alias resolves to the type it
names. A type alias and its target are the same type.

## Signature inference

From the providers in a set, classify every value type:

- **input**: required by some provider but produced by none. Inputs become the injector’s
  **parameters**.
- **output**: produced by some provider but consumed by none. Outputs become the
  injector’s **results**.

**Parameter ordering.** Inputs are deduplicated and emitted in a deterministic order: each
input type takes the source position of its *earliest* consuming provider, and the
parameters are sorted by that position, ties broken by comparing the types. So when one
provider is the earliest consumer of several inputs, those parameters are ordered by type,
not by that provider’s own argument order.

A type that is both produced and consumed internally is neither an input nor an output: it
is wired and disappears from the signature. Consequently, adding a provider that consumes
an existing output, or removing the last consumer of a type, **changes the inferred
signature**. This is by design.

**Unprovided means input, never an error.** There is no “missing dependency” diagnostic.
A typo in a type name, or a forgotten provider, simply makes that type an input and
*widens the signature*; it does not fail. This extends to a type no provider *can*
produce: a demand that matches a generic template by shape but pins a type its constraint
rejects becomes an input too, not an error (see [§5](#constraint-near-misses)). The `-v`
report exists so the user can catch this.

### Result ordering

The injector’s results appear in this order:

1. the value outputs,
2. the aggregated cleanup, if the set has any cleanup providers,
3. a trailing `error`, if the set has any fallible provider.

The value outputs are ordered deterministically by source position (see “Ordering and
determinism”).

## Ordering and determinism

Providers are emitted in **dependency order**: a provider is called only after the
providers producing its inputs. Concretely, the body is a topological order of the
dependency graph.

The order must be **deterministic** and **independent of read order**. Packages and files
may be presented to plumb in any order (the loader does not guarantee one); plumb must
produce byte-identical output regardless. Anchor every ordering decision to **source
position** (file name and offset within the shared position space), and break ties the
same way every run. Do not let map iteration order, package iteration order, or file
iteration order influence the output.

Two notes on ties. First, because each type has exactly one producer, the topological
order never has to choose between two producers of the same demand. The only freedom is
among providers that are *all* ready, and that is resolved by source position. Second,
source positions are globally unique within one load (every file occupies a distinct span
in the shared position space), so a position tie does not arise between two providers; an
implementation needs only a single, total position order, not a structural fallback. The
one tie left is several instantiations of a single template, which all carry the
template’s position: those stay in the order resolution created them, itself
deterministic, since instantiations arise in demand order (see
[§5](#the-resolution-algorithm)).

If the providers cannot be ordered (a **cycle**, where A transitively needs something B
produces and B needs something A produces), plumb reports the cycle, naming the providers
on it and the type each needs from the next. A provider that consumes its own output is a
single-node cycle.

## Errors

If **any** provider in the set returns a predeclared `error`, the injector gains a trailing
`error` result and becomes fallible. Each fallible call is checked immediately, and on
failure the injector returns at once.

Crucially, **a partially built value is never returned**. Every value output is held in a
local during the body and copied to its named result only on the **success path** at the
end; on an early error return, the value results stay zero.

```go
func build(cfg *Config) (store *Store, err error) {
	db, e := NewDB(cfg)
	if e != nil {
		err = e
		return
	}
	store2 := NewStore(db)
	store = store2 // outputs assigned only here, after the last fallible step
	return
}
```

At most one `error` result per provider is allowed; more is an error.

## Cleanup

A provider may return a **bare `func()`** to release what it just acquired, the
`(T, func(), error)` convention familiar from wire. plumb recognizes the bare `func()` as a
teardown hook, not a value: it never enters the type bag. Instead, the injector returns a
single **aggregated** cleanup, placed after the value outputs and before any error.

Required teardown semantics:

- **Reverse order.** Cleanups run last-acquired-first, both in the aggregated cleanup and
  on a mid-build error. If `OpenPool` (acquired after `OpenConn`) fails, the failure path
  runs `connCleanup()` before returning; the aggregated cleanup runs the newest cleanup
  first.
- **A failing provider does not have its own cleanup run.** A provider that returns an
  error is assumed to have cleaned up after itself, so the cleanup it returned on that call
  is not invoked.

```go
func build() (server *Server, cleanup func(), err error) {
	conn, connCleanup, e := OpenConn()
	if e != nil {
		err = e
		return
	}
	pool, poolCleanup, e := OpenPool(conn)
	if e != nil {
		connCleanup() // unwind what was acquired before, newest first
		err = e
		return
	}
	server2, server2Cleanup, e := OpenServer(pool)
	if e != nil {
		poolCleanup()
		connCleanup()
		err = e
		return
	}
	server = server2
	cleanup = func() {
		server2Cleanup()
		poolCleanup()
		connCleanup()
	}
	return
}
```

### Failable cleanups

A cleanup may report its own failure as `func() error` (e.g. `(*sql.DB).Close`). plumb
recognizes that too. When **any** cleanup in a set is failable, the aggregated cleanup
becomes `func() error`.

How the teardown errors are combined depends on **how many can combine**:

- A single failable cleanup with nothing else to join returns its error directly:

  ```go
  func setup(dsn string) (db *sql.DB, cleanup func() error, err error) {
  	db2, db2Cleanup, e := OpenDB(dsn)
  	if e != nil {
  		err = e
  		return
  	}
  	db = db2
  	cleanup = func() error {
  		cleanupErr := db2Cleanup()
  		return cleanupErr
  	}
  	return
  }
  ```

- When **two or more** errors can combine (two or more failable cleanups, or a failable
  cleanup plus a mid-build error to fold in), they are joined newest-first with
  `errors.Join`, which drops `nil`s (so a clean teardown still returns `nil`):

  ```go
  cleanup = func() error {
  	return errors.Join(newest(), older())
  }
  ```

  On a mid-build error, the build error is joined with whatever the unwound cleanups
  return.

The `errors` package is imported (and qualified) **only when an `errors.Join` is actually
emitted**, i.e. only when at least two errors can combine. A set with a single failable
cleanup and no later fallible step imports nothing.

## Value and pointer

plumb wires by **copy**, and it bridges between a value `T` and a pointer `*T` automatically,
in both directions, where `T` is a named type, a type parameter, or a predeclared basic type:

- **value needed as pointer (`T` → `*T`).** plumb holds the value in a local (a *fresh
  copy* of the source) and takes its address: `&x`. Every source copies the same way: a
  package variable, a struct field, a typed constant, a struct literal, or a function
  result is bound to a local and then `&local` is passed. Because the local is a copy, the
  `*T` never aliases the original storage, so mutating through the pointer never changes the
  source. Every consumer that needs the `*T` shares that one `&local`, so they see a single
  instance.
- **pointer needed as value (`*T` → `T`).** Dereference: `*ptr`. This assumes the pointer
  is non-nil; a nil dereference panics at run time, which plumb does not attempt to rule
  out statically.

This bridge applies where `T` is a named type, a type parameter, or a predeclared basic
type: `int`⇄`*int` bridges just like `MyInt`⇄`*MyInt`; an inline composite (a slice, map,
struct literal, etc.) has no dual. It is **one level**: plumb bridges `T`⇄`*T`, never
`T`⇄`**T` or a chain of them. It is not interface satisfaction and not conversion between
unrelated types.

The bridge is **producer-driven**: it fires only when a producer of one form covers a
demand for the other. When *neither* `T` nor `*T` is produced but both are demanded, the
two are unsatisfied independently and become **two separate injector inputs** (a `T`
parameter and a `*T` parameter), since matching is by exact type ([§7](#set-resolution),
“Unprovided means input”). The caller then passes what is morally one value twice; `-v`
shows both. Give one a producer, or a conversion between them, to collapse them.

## The generated file

- The file begins with a generated-code header matching the Go convention for
  machine-generated files (a line of the form `// Code generated <by-whom>. DO NOT EDIT.`).
  Tools, and plumb itself during regeneration, rely on this marker. Emit it.
- Then the `package <name>` clause, an import block (only for packages actually
  referenced), and one function per set.
- The output is **gofmt-canonical**: formatted exactly as `gofmt` would, with no synthetic
  source positions. (Producing text and running it through the standard Go formatter is a
  fine way to guarantee this.)
- Local variable names, the cleanup/error result names, and import aliases are an
  implementation choice, but must be collision-free within their scope and should be
  readable (derive value locals from their type or the producing provider; keep `err`/`e`
  for the error result/local when free).

## Not supported (by design)

- **Multiple distinct values of one type in a set.** Fundamental to the type-keyed model.
  Two parameters of one type always get the same value; two producers of one type are an
  ambiguity. To wire several values of one underlying type, use a slice `[]T` or array
  `[N]T` for a homogeneous collection, or a distinct defined type per use
  (`type ReadTimeout time.Duration` vs `type WriteTimeout time.Duration`). Decorators
  (`func(T) T` beside another producer of `T`) are ambiguous for the same reason; give the
  decorated value a distinct type.
- **Method providers on generic *constraint* interfaces** (see [§5](#generic-methods-fields-and-interfaces)).

# 5. Generic providers

A generic provider is a **template**: plumb instantiates it as the wiring demands, rather
than once. Whether instantiation is demand-driven depends on where the type parameters
appear:

- A template whose **result is generic** is instantiated **on demand**, once for each
  concrete type some consumer in the set pins its result to. A result-generic template that
  no consumer ever pins is never instantiated, which is an **error** (see “Rejections”).
- A template whose type parameters appear **only in its inputs**, producing a fully concrete
  result, is determinate and is **always** instantiated. It anchors the set: its result
  becomes an output (or is consumed), and any type parameter nothing pins is lifted to the
  injector (see “Free (unpinned) type parameters”). Such a template is never subject to the
  “unused” error, even if nothing consumes its result.

The subsections below introduce this behavior by example;
[the resolution algorithm](#the-resolution-algorithm) at the end of this section specifies
it: the matching rules, the dispatch order, when each ambiguity is decided, and the
orderings the outcome depends on.

## Pinned type parameters

A type parameter that some consumer fixes to a concrete type is instantiated there. The
**same provider may be instantiated at several types** within one injector:

```go
//plumb:build
func NewCache[T any]() *Cache[T] { ... }

//plumb:build
func NewUserService(c *Cache[User]) *UserService { ... }

//plumb:build
func NewSessionService(c *Cache[Session]) *SessionService { ... }
```

`NewUserService` needs `*Cache[User]` and `NewSessionService` needs `*Cache[Session]`, so
`NewCache` is called at both `User` and `Session`. Each concrete instantiation is a distinct
value of a distinct type; `*Cache[User]` and `*Cache[Session]` never collide.

The generated call **writes the type arguments explicitly** (`NewCache[User]()`). This is
always valid Go and is required when a type parameter is return-only (not inferable from the
arguments); plumb writes them in every case rather than deciding case by case whether
inference would suffice.

## Free (unpinned) type parameters

A type parameter that **nothing pins** is carried up to the generated function, which
becomes generic over it. Its constraint travels with it.

```go
//plumb:build
func NewPool[T any]() *Pool[T] { ... }

//plumb:build
func PoolSize[T any](p *Pool[T]) int { ... }
```

generates a function generic over the lifted parameter:

```go
func build[T any]() (int2 int) {
	pool := NewPool[T]()
	int3 := PoolSize[T](pool)
	int2 = int3
	return
}
```

(The output takes its name from its type, suffixed clear of the predeclared `int`; value
outputs are staged through locals and copied to the named results before the return, in
every set; see [§4](#errors).)

plumb keeps the template’s own parameter name where it can (here `T`), renaming only to
avoid a collision. The name must be a valid identifier that does not shadow anything the
body references unqualified (see “Naming” below and
[§6](#3-free-injector-type-parameter-rename-on-collision)).

A free parameter whose **constraint** is unexported and from another package cannot appear
in a separate-package signature; that is an error (see [§7](#cross-package-reachability)). A
constraint that does not type-check (an undefined name lifted into the header) is likewise
rejected: a located type-does-not-type-check error, not a crash (see
[§7](#directive-and-provider-validity)).

## Joint pinning (multi-result templates)

A template whose results span **different** type parameters is pinned **per result**, each
by its own consumer:

```go
//plumb:build
func NewKVPair[T, U any]() (Key[T], Value[U]) { ... }
```

plumb instantiates it when one consumer pins `Key[T]` and another pins `Value[U]`, e.g.
`NewKVPair[int, string]()` when the set needs `Key[int]` and `Value[string]`. The pins
need not surface together: when a pin arrives only after the template was already
instantiated with that slot lifted, plumb **revises** the earlier instantiation to carry
the union of the pins, restarting resolution with the union committed (see
[the resolution algorithm](#the-resolution-algorithm)), rather than splitting into a
second, half-pinned call. When the union is viable, one joint constructor stays one
call; a union the template’s constraints reject, or one entangled with a lifted
parameter, is refused and the split stands (see the algorithm’s refusal rule). The demands
that pin its results cluster into one binding per distinct pinning, so, like a single-result
template, it may be **instantiated several times** within one injector. If one consumer
needs `Key[int]`/`Value[string]` and another needs `Key[bool]`/`Value[byte]`, plumb emits
both `NewKVPair[int, string]()` and `NewKVPair[bool, byte]()`; the four results are distinct
types and never collide. A parameter that no demand pins on a given instantiation is lifted,
as for any template.

If another provider in the set already supplies one of a joint template’s outputs, plumb
does **not** reproduce it: that demand is already met, so the template is instantiated only
for its still-needed outputs, **lifting** the parameter the supplied result would have
pinned. With a direct `AlsoKeyInt() Key[int]` alongside `NewKVPair`, plumb takes
`NewKVPair[T, string]()` at a lifted `T` to build the needed `Value[string]` and leaves
`Key[int]` to the direct producer, rather than pinning `T = int` and producing `Key[int]`
twice. The instantiation still yields its other result at the lifted parameter (here
`Key[T]`), which, produced but unconsumed, becomes a value output of the injector
([§4](#signature-inference)). Dispatch follows the demands that are actually still open,
not whichever result a parameter happens to appear in.

A collision is only when two instantiations would **unavoidably** produce the **same output
type**: neither demand leaves a parameter free to lift around the duplicate. That is the
ordinary ambiguous-producer rejection (two producers of one type; see
[§7](#set-resolution)), not a separate joint-specific error.

Two *distinct* templates that could each build the **same still-open demand** are ambiguous:
the demand has no single producer, so source order must not pick one: plumb rejects it,
naming both. This is decided **after the constraint check**: a template whose constraint
rejects the pin cannot build the demand and does not compete, so a family of templates over
disjoint constraints, each serving a different demand, is fine. Lift-around is the
non-ambiguous case: there a *different* provider already supplies the demand, so it is no
longer open for a second template to compete over.

## Constraint near-misses

A demand can match a template’s result by **shape** yet pin a type that violates the
template’s type-parameter **constraint**, so the template cannot be instantiated there.
plumb treats this as it treats any unproducible type: the demand becomes an **injector
input** (per [§4](#signature-inference), “Unprovided means input”). plumb does not reject
it: a valid type that the only matching template happens not to produce is exactly the
unprovided-becomes-input case.

```go
type Box[T any] struct{ V T }           // Box: no constraint, so Box[int] is a valid type

//plumb:build
func Make[T Stringer]() Box[T] { ... }  // but Make requires Stringer

//plumb:build
func UseName(b Box[Name]) int { ... }   // Box[Name] — Name is a Stringer

//plumb:build
func UseInt(b Box[int]) string { ... }  // Box[int] — int is not a Stringer
```

`Box[int]` is a valid type, but `Make` cannot build it (`int` is not a `Stringer`), so
`Box[int]` becomes a parameter of the injector (the caller wires it in) while `Make` still
serves `Box[Name]`. A stricter producer coexisting with an externally supplied value is not
an error. (Rejecting a near-miss as a misuse is a tenable alternative design, but this spec
**requires** the permissive reading, so that no valid program is refused.)

The one case this turns into an error is when the near-miss leaves the template with **no**
successful consumer at all, then it is an unused result-generic template (see “Rejections”),
and the diagnostic names the failed constraint rather than merely “nothing pins its result”.
If the consumed type is *itself* an illegal instantiation (so the source does not
type-check), plumb is best-effort: it does not crash, but the output may carry the user’s
own type error: invalid input is outside the compilable-output guarantee.

## Generic methods, fields, and interfaces

- **Generic-receiver methods** are supported. The receiver value already carries its type
  arguments, so the call needs none: `func (c *Cache[T]) Snapshot() *Snapshot[T]` emits
  `cache.Snapshot()`.
- **Fields on generic structs** are templates, equivalent to `func(Foo[T]) Baz[T]`, with the
  struct as input (taken by value or pointer like any field provider):

  ```go
  type Foo[T any] struct {
  	//plumb:build
  	Bar Baz[T]
  }
  ```

- **Methods on generic *basic* interfaces** are templates. A *basic* interface is one whose
  type set is exactly its methods (no embedded constraints like `comparable` or unions). It
  is equivalent to `func(Source[T]) Result[T]`, with the interface as input:

  ```go
  type Source[T any] interface {
  	//plumb:build
  	Fetch() Result[T]
  }
  ```

- **Methods on generic *constraint* interfaces are rejected.** A non-basic interface (one
  embedding `comparable`, a union, or another constraint) can only be used as a type
  constraint, never as the type of a value, so it cannot be a receiver. (This is the same
  rejection as a method provider on a non-generic constraint interface.)

## Rejections specific to generics

All produce a clear, located error (see [§7](#generics)):

- a **result-generic** template that no consumer in the set ever instantiates (nothing pins
  its result’s type parameter), naming the set; a template with a fully concrete result is
  always instantiated and is never subject to this error. If every consumer that would pin
  it does so at a type its constraint rejects (a constraint near-miss, above), the message
  names that failed constraint instead;
- a **bare type-parameter result** (`func Default[T]() T`), or a **pointer to one**
  (`func Default[T]() *T`): it would match every demand: the pointer form matches every
  pointer demand and, through the value/pointer bridge (see [§4](#value-and-pointer)),
  every value demand;
- two distinct templates that could each **build one still-open demand** (whether by fully
  pinning it or by producing it jointly), decided after the constraint check, so a
  disjoint-constraint family each serving a different demand is fine;
- a template whose **instantiation does not terminate**: a provider that manufactures
  unboundedly larger types (each instantiation demanding a strictly deeper one, e.g.
  `Box[T]` consumed to produce `Box[Box[T]]`) so the demand never closes. plumb bounds the
  instantiation depth and reports this rather than looping forever; depth is measured
  through nested function, struct, and interface types too (not only named-type or
  pointer-like nesting), so a template that grows *through* a function type (needing
  `Box[func(T)]` to produce `Box[T]`, manufacturing `Box[func(func(…))]`) trips the same
  bound;
- a template **instantiated at an unexported type** that cannot be named from a separate
  destination package;
- a free injector parameter with an **unexported constraint** (named type or a literal
  interface/union mentioning an unexported type) in a separate-package signature.

## Naming (interaction with same-package output)

A lifted free type parameter shares the generated function’s scope with everything the body
references unqualified. In same-package generation, that includes same-package provider
calls and bare self types. The lifted parameter’s name must therefore **not equal** any
such identifier, or the parameter would shadow it and the call would no longer name the
provider. plumb renames the lifted parameter to avoid the collision (for example, a free
parameter that would be `A` next to a same-package provider `A` becomes `A2`). See
[§6](#3-free-injector-type-parameter-rename-on-collision) for the full collision model.

## The resolution algorithm

The subsections above introduce generic resolution by example; this one specifies it (the
matching rules, the dispatch order, when each ambiguity is decided, and every ordering the
outcome depends on) precisely enough to predict, for any input, which instantiations are
made and which rejection fires first. It specifies observable behavior only; how an
implementation memoizes or represents any of it is its own business.

### Definitions

**Supply and demand.** Resolution tracks a *supply* (each produced type, mapped to the
instance producing it) and a *demand set*, every input type of every instance made so
far. (A struct-field provider’s implicit receiver demands the struct’s value form; whether
the emitted access goes through the value or the pointer is settled after resolution, per
[§3](#struct-field-providers).) A demand is **satisfied** when the supply holds it exactly
or holds its value/pointer dual ([§4](#value-and-pointer)). Registering an output whose
exact type the supply already holds is the ambiguous-producer rejection
([§7](#set-resolution)); a demand that ends the solve unsatisfied is not itself a
rejection: it becomes an injector input ([§4](#signature-inference)), subject to the
same validity and reachability checks as any other signature type
([§7](#cross-package-reachability)).

**Provider classes.** Every provider in the set is one of:

- **concrete**: not generic; instantiated unconditionally;
- **anchor**: generic, but no value result mentions its own type parameters; instantiated
  unconditionally, exactly once, every parameter lifted;
- **template**: generic, with a value result mentioning at least one of its type
  parameters; instantiated on demand, possibly several times, possibly never (then
  rejected as unused).

Classification examines providers in source-position order and validates each result
shape as it goes: a provider with more than one error result is rejected there
([§3](#cleanup-and-error-results)), as is a template with a value result that **is** a
bare type parameter or a pointer to one (see
[Rejections](#rejections-specific-to-generics)), so the first invalid provider by
position is the one reported. Within one provider, the error-result count is checked
before the bare-type-parameter test: a template returning `(T, error, error)` is rejected
for the error results.

**Unification.** A template result *matches* a demand when the two agree structurally,
treating the template’s own type parameters (and nothing else) as variables:

- aliases are unwrapped on both sides, at every level;
- a type parameter matches whatever stands opposite it and **binds** to it; a parameter
  that appears twice must bind both times to identical types;
- a pattern part that mentions no parameter must be identical to its counterpart;
- a named type matches only the same named type, with type arguments unifying pairwise;
- compound shapes must agree exactly in pointer/slice/array/channel/map structure, array
  lengths, channel directions, struct field names, embedding, and tags, full interface
  method sets, function-signature shape including variadicity, with their elements
  unifying.

The outcome is a **binding**: concrete type arguments for the parameters the demand pins.
A demand may itself mention a previously lifted injector parameter; it is opaque here,
matching like any other concrete type, by identity.

**Pinnable cover.** A template’s *pinnable* parameters are those appearing in any of its
value results. A binding **covers** when it pins every pinnable parameter. A parameter
appearing only in inputs is never pinnable.

**Viability.** A binding is *viable* when the template actually instantiates at it: pinned
parameters at their bound types, every other parameter at a fresh lifted parameter, every
constraint satisfied. A match whose binding is not viable is a **constraint near-miss**
(see [Constraint near-misses](#constraint-near-misses)): it produces nothing and does not
compete for the demand. Every covering near-miss, and every near-missing joint cluster,
is recorded as the template’s reason, reported if the template ends the solve unused,
whether or not a rival served the demand.

**Lifting.** Instantiating at a binding that leaves parameters unpinned puts a fresh type
parameter on the generated function for each (see
[Free (unpinned) type parameters](#free-unpinned-type-parameters)). The fresh parameter
carries the original’s constraint, with references to the template’s parameters (the
lifted one itself included) substituted by their resolution, the pinned type or the
corresponding lifted parameter: pinning `T = int` in `func F[T any, U interface{ ~[]T }]`
lifts `U` constrained by `interface{ ~[]int }`. Its name is the original’s (a blank or
unnamed parameter lifts as `T`), suffixed (`U`, `U2`) whenever the name is taken: by an
earlier lifted parameter, by any predeclared identifier, or by any top-level identifier
of the destination package outside the file being overwritten (plumb’s own prior output
reserves nothing, keeping regeneration idempotent). That reservation set is a deliberately conservative superset
of what the body could reference unqualified (see
[Naming](#naming-interaction-with-same-package-output)). The
generated header lists lifted parameters by origin-template position, then parameter
index; two lifts of one parameter (one per instantiation) keep the order their
instantiations were made.

### The algorithm

Providers are considered in source-position order throughout; demands in **canonical type
order**: a fixed order computed from the types alone, never from addresses, load order,
or source position. Aliases are unwrapped, then kinds compare first (basic < pointer <
slice < array < channel < map < function < struct < interface < defined type < type
parameter), then structure within a kind: basics by their `go/types` kind constant
(`bool < int < int8 < … < uintptr < float32 < … < string`, with `byte` and `rune`
unaliased), defined types by package path, then name, then type arguments pairwise, and
compound types by shape first (array length, channel direction, function variadicity,
struct/interface member count), then member-wise in declaration order (a struct field’s
name, embeddedness, and tag before its type; a map’s key before its element; a function’s
parameters before its results). Distinct types can compare equal only in corners that
never co-occur in one demand set (two type parameters sharing name and index), so the
order is total wherever the algorithm sorts. Resolution stops at the first rejection it
reaches.

1. **Classify** every provider as above, in source order, validating result shapes as
   defined: the first provider with more than one error result or a bare-`T`/`*T` value
   result is the rejection reported.

2. **Seed.** Instantiate every concrete provider, then every anchor. Every instantiation
   made in any step registers its value outputs in the supply (rejecting a duplicate)
   and adds its inputs to the demand set.

3. **Single-demand step.** Scan the unsatisfied demands in canonical order. For each
   demand *d*, the *candidates* are the templates with a value result that matches *d* in
   a covering, **viable** binding: each template offers its first such result in result
   order, and every covering result whose binding fails viability is recorded as a
   near-miss along the way. If no template offers one, the same matching runs once
   against *d*'s dual (an instance made this way supplies the dual, satisfying *d*
   through the bridge). Then, by the number of candidates:

   - **two or more**: rejected as ambiguous templates, naming the first two in position
     order. A near-miss does not compete: a family of same-shaped templates over disjoint
     constraints resolves each demand to its single viable member;
   - **exactly one**: instantiated, unpinned parameters lifted; the step restarts on a
     fresh scan, so demands the new instance adds surface immediately;
   - **none**: *d* is skipped (it stays open, for the joint step or the signature) and
     the scan continues.

   When a full scan instantiates nothing, resolution proceeds to step 4.

4. **Cross-template check.** If any unsatisfied demand can be produced by two or more
   distinct templates (some value result matches it, covering or not, in a viable
   binding; when no template’s result matches the demand’s exact form, the same test runs
   against its dual), that is the same ambiguous-templates rejection, naming the two
   lowest-positioned producers and the contested type (the demand, or the produced dual
   form when the dual is what matched), for the first such demand in canonical order. A demand another
   provider already supplies is satisfied, so it is not scanned here: that is what keeps
   lift-around (see [Joint pinning](#joint-pinning-multi-result-templates)) out of the
   ambiguity, and it includes a demand a covering template won in step 3. Full pinning
   preempts joint production deterministically, so the covering template serves the
   demand and a rival that could produce it only jointly is not ambiguous with it; the
   rival lifts around the now-supplied demand like any other.

5. **Joint step.** For each template in position order, the unsatisfied demands are
   clustered into instantiations:

   - Scanning demands in canonical order, each demand offers one candidate binding per
     value result it matches, in result order (its exact form first, its value/pointer
     dual when none of the template’s results match the exact form), counting only
     bindings that pin at least one parameter. A parameter-free result never drives instantiation; its output
     arrives (identically) with every instantiation the other results drive, so a second
     instantiation is the duplicate-output rejection above.
   - A demand joins the first existing cluster (in creation order) it can: the merged
     binding is the demand’s first candidate, in result order, that agrees with the
     cluster on every shared parameter **and** keeps the merge viable. Otherwise it seeds
     a new cluster from its first viable candidate, or, when every candidate is a
     near-miss, from its first candidate, so the near-miss is recorded; the demand then
     stays open for a later template or pass, and failing those, the signature.
   - Each cluster is instantiated once, unpinned parameters lifted; the same template is
     never instantiated twice for the same pinning. A near-miss cluster records its reason
     and produces nothing.

   The first template whose clusters produce an instance sends resolution back to step 3.
   When neither step 3 nor step 5 produces an instance, the fixpoint is complete: every
   remaining unsatisfied demand becomes an injector input.

   **Pinning revision.** Steps 3 and 5 instantiate through one funnel, and the funnel
   merges before it splits. A binding entering the funnel, a viable candidate or a
   would-be near-miss alike, while an existing instance of *p* (the earliest compatible
   one, in creation order) carries a **compatible** pinning the binding would extend
   (the two agree on every slot both pin) does not create a second, half-pinned instance
   when the union of the two pinnings is viable and mentions no lifted parameter;
   viability is judged on the union, after merging. Instead the union becomes a
   **committed pinning** for *p*, and resolution restarts from step 2 with the commitment
   in force: at instantiation time a binding compatible with a committed pinning is
   merged into it, so the replay produces the one instance carrying the union (slots
   outside it lift as usual) and every demand that mentioned an abandoned lifted
   parameter of the union’s slots now dispatches at its concrete form, so the ambiguity
   checks of steps 3 and 4 judge types the user can name. A union extending an existing
   commitment upgrades it **in place**, keeping a template’s commitments pairwise
   incompatible (so the compatible commitment is unique) and letting chained late pins
   converge instead of re-deriving the extension on every replay; a union the replay
   re-derives without extending anything is already in force and commits nothing. A
   union that is not viable, or that mentions a lifted parameter (which cannot survive
   the restart), is **refused** and recorded: a refusal never restarts, the instances
   stand, and resolution proceeds exactly as without the rule: the fallback is the
   split, never a rejection. Two instances whose pinnings conflict on a shared slot are
   the ordinary multi-instantiation case and never merge.

6. **Unused templates.** A template that produced no instance is rejected
   ([§7](#generics)): with the first near-miss reason recorded for it, if any; otherwise,
   scanning demands in canonical order, at the first demand it could serve (by covering
   match, dual included) that another provider actually supplies, as shadowed by that
   producer; otherwise as pinned by no consumer.

Instances are deduplicated by template and full type-argument list, so re-deriving the
same instantiation from different demands is a no-op, not a duplicate output.

### Termination

Demand-driven instantiation can be driven unboundedly, each instance demanding a strictly
deeper type (see [Rejections](#rejections-specific-to-generics)), so an implementation
**must** bound it and reject on the bound ([§7](#generics)). Two bounds on demand-driven
template instantiation, each far above any real program (seeded concrete and anchor
instances, whose types the user wrote out literally, count toward neither): the number of
retained instantiations per set (currently 5000), and the structural depth of any value
type an instantiation produces (currently 40; checked before the count), measured through
every compound form (type arguments, pointers, slices, arrays, maps, channels, and
function, struct, and interface types alike). Every pass of steps 3–5 either retains an
instance or ends the fixpoint, so the bounds imply termination. Pinning revision adds
restarts, and each restart either extends a committed pinning in place (bounded by the
template’s parameter count) or adds a commitment for a distinct instantiation family
(bounded by the instantiation count), so restarts are bounded too; an implementation
**must** cap them and reject as non-terminating at the cap.

### The loop at a glance

Non-normative; the numbered steps above govern.

```
restart:                                  # re-entered with commitments in force
classify: concrete | anchor | template     (reject bare T and *T results)
instantiate every concrete, then every anchor (all parameters lifted)

instantiate(p, bind):                      # the one funnel steps 3 and 5 use
  bind ∪= first committed pinning of p compatible with bind
  if an existing instance of p is compatible with bind:
    union viable and lift-free -> commit union; goto restart
    else                       -> refuse once; proceed (the split stands)

loop:
  for d in unsatisfied demands, canonical order:          # step 3
    V ← templates with a covering, viable binding for d
        (covering near-misses recorded along the way)
    if V empty: V ← the same matching against d's dual
    if |V| ≥ 2: reject ambiguous templates
    if |V| = 1: instantiate it; continue loop             # else d stays open
  for d in unsatisfied demands, canonical order:          # step 4
    if two templates produce d (or its dual) viably: reject ambiguous templates
  for p in templates, position order:                     # step 5
    cluster unsatisfied demands over p's results          # exact form, else dual
    instantiate p once per new cluster (unpinned lifted)  # agree + stay viable
    if anything instantiated: continue loop
  break                                       # leftovers become injector inputs

reject unused templates    # near-miss reason > shadowed by producer > unpinned
```

# 6. Packaging, qualification, and output safety

## The destination is an import path

The generated file belongs to some package, the **destination**. The destination is
identified by its **import path** (`-import-path`), *not* by where the file is written
(`-output`). Two packages may share a name at different paths, and the output may even be
standard output; the import path is what decides qualification.

- A provider or type **in the destination package** is referenced **unqualified** and not
  imported (it lives in the same package as the generated file).
- A provider or type **in any other package** is **imported and qualified** (`pkg.NewX`),
  and so must be exported.

Resolving the destination (see also [§1](#-import-pathpath)):

- `-import-path` given → that path is the destination.
- omitted, exactly one scanned package → that package (the common `go:generate` case).
- omitted, more than one scanned package → ambiguous; require `-import-path`.

The destination’s import path may **match a scanned package** (*same-package* generation,
like wire’s `wire_gen.go`) or **match none** (*separate-package* generation, where every
provider is imported and qualified, and `-package-name` is required because there is no
scanned package to take the name from).

### Multiple packages

`./...` scans many packages, and a set’s providers may live in several of them. The
destination decides which are unqualified:

```go
// package store
//plumb:build
func NewDB(cfg *Config) (*DB, error) { ... }

// package web (imports store)
//plumb:build
func NewServer(db *store.DB) *Server { ... }
```

- `-import-path=example.com/app` (a separate package) imports **both** `store` and `web`.
- `-import-path=example.com/web` generates into `web`: `web`'s providers are unqualified,
  only `store` is imported, and `-package-name` is inferred as `web`.

## Output safety in same-package mode

When the generated file joins an existing scanned package, its **import block** and its
**function names** share a namespace with that package’s existing top-level declarations.
Go forbids an identifier appearing in both a file’s import block and the package block, and
forbids two package-level declarations of one name. So a naively chosen name can collide
with a declaration plumb did not otherwise touch, producing code that does not compile, in
violation of the central invariant.

plumb reads the destination package’s existing top-level identifiers (and the import
qualifiers its files use) and avoids collisions with three mechanisms. (These require the
destination to be a *scanned* package; see “When the destination is not scanned,” below.)

### 1. Import qualifiers: alias on collision

An import whose natural qualifier equals a destination identifier is given an alias.
Example: the destination declares `type url struct{}`, and a provider needs `*url.URL` from
`net/url`. The import is aliased so it does not redeclare the local `url`:

```go
import url2 "net/url"
func build(...) ... { ... url2.URL ... }
```

The same applies to the `errors` package that a failable cleanup needs for `errors.Join`:
if the destination declares any `errors` identifier, the import becomes `errors2`. Because
plumb chooses its own import qualifiers, this collision is always *resolved* by aliasing,
never reported.

An import qualifier must avoid the **whole** destination scope (it lives in file scope and
cannot coexist with any package-level name). For simplicity and safety plumb also keeps
**local variable** names off the whole destination scope, even though a local could legally
shadow a package-level name the body never references; the only cost is an occasional
numeric suffix, and the rule is uniform.

### 2. Generated function name: reject on collision

A generated function is named after its set and **cannot be aliased**. If the set name is
already declared in the destination package, plumb **rejects** with a “rename the set”
diagnostic, *except* for the declaration in the file plumb is about to overwrite, so that
regenerating over plumb’s own prior function still works.

The same rejection applies when the set name equals an **import qualifier** used in a
hand-written file of the destination package: Go forbids one identifier in both that file’s
import (file) block and the generated function’s package block, and plumb cannot rewrite the
hand-written file, so the function name cannot be made to coexist. This is reported, not
auto-resolved, unlike case 1, where plumb controls the qualifier.

- Identify “the file being overwritten” by the **base name** of `-output` (a package’s
  files share one directory, so base names are unique within it; this avoids absolute/
  relative/symlink path-matching hazards). The uniqueness premise assumes the output
  resolves into the package’s own directory; an `-output` written **elsewhere** must not
  share a base name with a destination source file, or that file is treated as plumb’s
  prior output: its providers ignored and its declarations dropped from the collision
  safeguards. This is a deliberate trade for path-robust matching; name the outside
  output distinctively (`plumb_gen.go`).
- When writing to **standard output**, plumb cannot tell which file it would replace, so
  the package-declaration collision check is **skipped**.
- `init` never appears as a package-level declaration (Go does not enter it into the package
  scope and allows several `init` functions), so a set named `init` is never a collision
  here; its legality is governed only by the reserved-name rule (see [§7](#reserved-and-colliding-names)).

### 3. Free injector type parameter: rename on collision

A lifted free type parameter (see [§5](#free-unpinned-type-parameters)) shares the function
scope with everything the body references unqualified. In same-package mode that includes
same-package provider calls and bare self types. A free parameter whose name equals such an
identifier would shadow it. plumb **renames** the parameter (e.g. `A` → `A2`) so the
unqualified reference still resolves to the intended symbol. The parameter must also avoid
the predeclared identifiers the body emits bare (`new`, `nil`, `error`, the basic type
names, and so on).

## When the destination is not scanned

All three safeguards need plumb to *see* the destination’s declarations, which it can only
do when the destination is one of the scanned packages. A `-import-path` matching **no**
scanned package (a separate package, or one the patterns simply did not load) leaves
plumb blind to those declarations.

In that case plumb cannot guarantee a generated qualifier or function name avoids a
collision with an unseen declaration. This is a documented limitation: to get collision-
safe output, **include the destination package in the scanned patterns**. (In pure
separate-package mode where the destination is a brand-new package containing only the
generated file, there is nothing to collide with, so this is moot; the risk is a
*pre-existing, unscanned* destination package.)

## Import-cycle destinations

The destination’s import path determines what the generated file imports: every provider
or type it references outside the destination is imported and qualified
([§3](#3-provider-kinds)). If one of those imported packages (directly or transitively)
imports the **destination** back, the generated file would close an import cycle and not
compile, even though the providers themselves are valid Go.

This arises only in a multi-package scan whose destination is *upstream* of a provider
package the injector uses: for example, generating into `example.com/store` an injector
that calls a provider in `example.com/web`, where `web` imports `store`. The common
single-package `go:generate` cannot reach it (with only one scanned package every provider
is same-package and unqualified, so the generated file imports no provider package to close
a loop back).

plumb does **not** detect this. Catching it reliably needs the full source-level import
graph, which plumb deliberately does not load (it type-checks with a reduced mode, and a
package reached only through compiler export data reports an incomplete import list). Rather
than detect cycles approximately (reporting some while silently emitting others), plumb
emits the file and lets the **Go compiler** report the cycle at build time (“import cycle
not allowed”). This is the one place where the “valid input produces compilable output”
expectation is delegated to the compiler rather than enforced by plumb. The fix is to
choose a destination that none of its providers’ packages import (commonly a separate
package that imports them all).

## Regeneration

Re-running plumb over its own output must be safe and is part of the invariant:

- **Idempotent / corrective.** Running again reproduces the file, or updates it if providers
  changed.
- **Tolerate a stale generated file.** In same-package mode plumb re-scans the package whose
  file it is about to replace. That prior generated file may no longer compile. A provider
  whose signature changed, or one since removed, leaves the old wiring type-incorrect.
  plumb must **not** be blocked by such type errors: it should still load the package
  (reading provider types directly, which remain well-formed) and regenerate the corrected
  wiring.

### Classifying load failures

plumb separates **fatal** load failures from **tolerable** ones:

- **Fatal.** The package cannot be safely scanned: a **parse error** (it could hide a
  `//plumb:` directive), or a structural failure the Go toolchain reports for the load as a
  whole (a **broken module**, **no package matched** the patterns).
- **Tolerable.** Anything that still leaves a parseable, type-resolvable package: in
  particular a **type error**. This includes a stale generated file’s broken wiring *and* an
  **unresolved import** (which, without type-checking the dependency graph, surfaces as a
  “could not import” type error). These are collected, not fatal.

An unresolved import that the generated output would actually name surfaces precisely
downstream as an invalid-type diagnostic (see [§7](#directive-and-provider-validity)); one
that the output never references is harmless. Either way, plumb does not refuse to run.

When plumb tolerates load errors and then **generation fails** for some other reason, it
**surfaces the tolerated errors**, so a genuine provider type problem is not swallowed
behind a downstream diagnostic. (On a non-verbose success they are not shown, since a
stale-output type error is expected and benign. But `-v` surfaces them, so a
not-fully-type-correct load is not silently swallowed.)

# 7. Diagnostics

plumb either succeeds (emitting compilable code) or fails with a clear error. This section
catalogues every condition that must be an **error**, and the one thing that deliberately
is **not**.

General requirements for errors:

- **Located.** Anchor each diagnostic to a source position (`file:line:column`): the
  offending provider, type, or directive. Set-level diagnostics that no single provider owns
  should anchor to a stable, source-earliest position within the set.
- **Actionable.** Name the offending identifier and say what to do (rename, add a consumer,
  give a type, export it, name a source type, …). The exact wording is not contractual;
  the *condition* and the *information conveyed* are.
- **Fail before writing.** On any error, write nothing to the output and exit non-zero.

The position columns below are illustrative.

## The deliberate non-error

- **Unprovided type → input, not an error.** A type required but produced by nobody becomes
  a parameter of the injector. There is no “missing dependency” error; a typo silently
  widens the signature. `-v` is how the user catches it. This includes a generic
  constraint near-miss whose template is used elsewhere (see [§5](#constraint-near-misses)).
  Do **not** turn this into an error.

## Directives in test files: a known limitation

plumb does not scan test files. A `//plumb:` directive in a `_test.go` file is neither
honored nor reported: it produces no provider and no diagnostic.

This is the **one exception** to plumb’s rule that a recognized directive is never
silently dropped (every other unreachable directive position is a located error: a stray comment, an empty
declaration group, a blank name). The exception is deliberate:
because a Go test declaration is visible only inside its own directory’s test binary, a
test-file provider could be wired only into a generated `_test.go` file in that same
directory, and supporting that end to end (loading test package variants, collapsing the
several the loader returns for one import path, a distinct test-output destination) is
disproportionate to the need. A provider a test must inject belongs in a regular file, or
is constructed by hand in the test.

Consequences to keep in mind:

- A set whose directives live **only** in test files does not exist; if that was the only
  directive in the run, plumb reports “no directives found” (see
  [No directives found](#no-directives-found)), not a located error at the ignored
  directive.
- The same-package collision safeguards (see [§6](#reserved-and-colliding-names)) do not
  see identifiers declared in the destination package’s test files, since those files are
  never loaded.

## Directive and provider validity

- **Malformed set name.** A comment recognized as a `plumb:` directive whose name is not a
  valid Go identifier (`//plumb:123`), or that carries trailing arguments
  (`//plumb:build extra`), is rejected. (A comment not recognized as a directive at all is
  silently ignored; see [§2](#malformed-directives).)
- **Well-formed directive in an unsupported position.** A recognized `//plumb:` directive
  is rejected, not silently ignored, when it sits where no provider can attach: inside a
  function body (including on a function-local declaration), on an import spec, or
  free-floating between declarations. (Contrast an *unrecognized* comment, which is silently
  ignored; see [§2](#malformed-directives).)
- **`//plumb:` on a non-struct type** (a defined non-struct type, an interface, or a type
  alias whose target is not a struct): rejected. Struct-type providers require a struct.
- **Untyped constant provider**: a `//plumb:` constant without an explicit type has no
  determinate provided type; rejected. Ask for an explicit type.
- **Blank provider**: a `//plumb:` directive whose target is named with the blank identifier
  declares nothing that can be wired or referenced, and is rejected the same way for every
  placement: a blank function or method (`func _()`, `func (R) _()`), a blank type
  (`type _ struct{…}`), a wholly-blank struct-field group (`//plumb:` + `_ int`), an
  all-blank multi-name `var` (`var _, _ = …`), or a blank `const` (`const _ …`); give it a
  name. A directive on a **member** of a blank-named type is rejected too, since the member
  cannot be reached through a blank receiver. Two forms keep a blank name legal: a *single*
  blank `var` with an explicit target type is instead the conversion form (see
  [§3](#3-provider-kinds)), and a blank name **mixed** with named ones in one group
  (`A, _ int`) is skipped: only the named entries become providers.
- **`func init` provider**: a directive on `func init()` is rejected: Go forbids
  referring to `init` from anywhere, so an emitted call could never compile, and a package
  may declare several. A *method* named `init` is an ordinary selector and stays allowed,
  and a *set* named `init` is unrelated and supported.
- **Conversion with no concrete source** (`var _ T = nil`): the untyped `nil` names no
  source type; rejected. Tell the user to write `(*Concrete)(nil)`.
- **Identity conversion** (source type identical to the target, e.g. `var _ MyInt = 5`, or
  a conversion between a type alias and the type it names): consumes and produces the same
  type; rejected.
- **Provider directive on an embedded struct field**: rejected. Ask the user to name the
  field.
- **Provider directive on an embedded interface**: rejected. Ask the user to put the
  directive on a method instead.
- **Method provider on a constraint interface** (generic or not): rejected. A constraint
  type cannot be the type of a value, so it cannot be a receiver.
- **A provider that references a type that does not type-check** (an undefined name or
  unresolved import), where the reference is one plumb’s output would actually name:
  rejected. Beyond the injector’s own input and output types, this covers a **method
  receiver that does not resolve** (a typo’d or undefined receiver type) and a **lifted free
  type parameter whose constraint does not type-check** (an undefined constraint on a
  template whose parameter is lifted into the injector header; see
  [§5](#5-generic-providers)). Each is reported as a located type-does-not-type-check error,
  never a crash. (This is distinct from tolerated stale-output type errors; see
  [§6](#regeneration). The distinction: a type
  error in *what plumb must emit* is fatal; a type error confined to the prior generated
  file being replaced, or to an unresolved import the output never names, is tolerated.)

## Set resolution

- **Ambiguous producer**: two providers in a set produce the same type; name both, with
  their positions. A single provider returning **two values of the same type** is the same
  error, as is a multi-name `var`/`const` declaring two names of one type.
- **Duplicate directive**: the same set directive naming a declaration twice (whether
  repeated in one comment group, or named by both an enclosing group directive and a spec
  inside the block) is rejected, naming the set and the redundant directive to remove.
- **Multiple `error` results** from one provider: at most one is supported; rejected.
- **Dependency cycle**: the providers cannot be ordered. Report the cycle as a path
  (`A needs T1 → B needs T2 → … → A`). A provider consuming its own output is a single-node
  cycle.

## Generics

- **Unused result-generic template**: a template whose result is generic and which no
  provider in the set instantiates (nothing pins its result’s type parameter). Name the set;
  suggest removing it or adding a consumer. (A template with a fully concrete result is always
  instantiated as an anchor and is *not* subject to this error; see [§5](#5-generic-providers).)
  When the template went unused because its only would-be consumers pin its result at a type
  its constraint rejects (a *constraint near-miss*), the message reports that constraint
  failure rather than “nothing pins its result”. A near-miss whose template *is* used
  elsewhere is not an error: the unproducible demand becomes an injector input (see
  [§5](#constraint-near-misses)).
- **Bare type-parameter result** (`func Default[T]() T`), or a pointer to one
  (`func Default[T]() *T`, which matches every pointer demand and, via the value/pointer
  bridge, every value demand): would match every demand; rejected.
- **Ambiguous templates**: two distinct templates that could each build one demand, whether
  each fully pins it (single-result) or they produce it jointly, decided after the
  constraint check; rejected, naming both. A template that lifts around a demand another
  provider already supplies is not ambiguous (see [§5](#5-generic-providers)).
- **Non-terminating instantiation**: demand-driven instantiation does not close because a
  provider manufactures unboundedly larger types (each instantiation demands a strictly
  deeper one). Depth is measured through nested function, struct, and interface types too,
  not only named-type or pointer-like nesting (see [§5](#5-generic-providers)). plumb bounds
  the instantiation depth and reports this as an error rather than looping; the message
  should name the offending (truncated) type and the depth bound. An implementation **must**
  bound this: an unbounded solver loop on adversarial input is a defect, not acceptable
  behavior.

## Cross-package reachability

When the generated file is in a different package from a provider (separate-package, or a
destination that is not the providers’ own package), everything it must name across the
boundary has to be exported and reachable:

- **Unexported provider** referenced from the generated package: rejected.
- **Unexported type in the inferred signature** (an input/output type, or a type argument
  of a generic instantiation that surfaces in the signature): rejected.
- **Unexported constraint** on a lifted free type parameter (a named constraint, or a
  literal interface/union mentioning an unexported type): rejected, since the constraint
  appears in the generated header.

plumb checks that cross-boundary names are **exported**, but not that the destination can
actually **import** their package, so two cases produce uncompilable output reported by the
Go compiler rather than by plumb: a provider or type in a `.../internal/...` package whose
destination is outside that internal subtree (`use of internal package not allowed`), and a
provider or type in a `package main` (`import "…" is a program, not an importable package`).
Choose a destination that can import every provider’s package.

## Reserved and colliding names

- **Reserved function name with a non-empty signature.** A set named `init` (any package),
  or `main` in `package main`, would generate a function the Go compiler forbids if it has
  any parameters or results: `func init`/`func main` must take none. Reject when the
  inferred signature is non-empty. An empty-signature `init`/`main` is allowed (a valid
  `func init()` that wires package-level side effects, for instance).
- **Set named after a predeclared identifier.** A set whose name is a predeclared identifier
  (`int`, `new`, `error`, `any`, …) would, as a package-block function declaration, shadow
  that identifier for the whole destination package, breaking the generated body and any
  sibling file that uses the builtin. The function name cannot be aliased, so reject any such
  set name outright, in both same- and separate-package modes.
- **Destination declaration shadows a predeclared identifier.** The reverse direction: a
  scanned destination file (other than the one being overwritten) declaring a top-level
  `error`, `string`, `nil`, … captures the predeclared spellings the generated file writes
  unqualified (`error` and `nil` in fallible wiring, basic-type names in signatures) and
  no qualification can restore a shadowed builtin. Rejected outright, regardless of
  whether the plan happens to spell the name, on the same trade as the set-name rule.
- **Set name collides with a destination declaration** (same-package, destination scanned,
  not the file being overwritten): rejected with a “rename the set” diagnostic. The same
  applies to a set name equal to an import qualifier used in a hand-written destination
  file. See [§6](#2-generated-function-name-reject-on-collision). In stdout mode plumb
  cannot tell which file it would overwrite, so the existing-declaration half of this check
  is skipped and such a collision surfaces only at compile time.

(An import qualifier *plumb itself* chooses, and a free type parameter, are *resolved
automatically* by aliasing/renaming, not reported. See [§6](#output-safety-in-same-package-mode).)

## No directives found

If the scan finds no `//plumb:` directives at all, there is nothing to generate; report it.

## Internal invariants (panics, not user errors)

Some conditions can only arise from a bug in plumb itself, never from valid user input
(for example, an unhandled type form when rendering, an ordering invariant violated after
the cycle check, or a provider skeleton that fails to instantiate at its own type
parameters). The reference implementation treats these as **fail-loud panics** rather than
returned errors, on the principle that they are unreachable from valid input and a silent
miscompile is worse than a crash. An implementer should likewise distinguish *user errors*
(returned, located, actionable) from *broken internal invariants* (loud failure), and must
ensure the latter are genuinely unreachable from valid input. The fuzz target (see
[§8](#8-implementation-and-testing-guidance)) is how you gain that confidence.

# 8. Implementation and testing guidance

This section is advisory. The rest of this document is the **contract**; this is help on
building a high-quality implementation of it.

## Design principles

You are implementing a compiler-shaped tool: it reads a typed program, analyzes it, and
emits another program. That puts a few principles above the rest. Treat these as a way of
thinking, not a blueprint. **The decomposition into packages, types, and passes is yours to
choose. Do not copy any particular pipeline or intermediate representation; design the one
that fits the language and tools you build with.**

- **Push I/O to the edges; keep a pure core.** Loading packages, reading flags, and writing
  files are boundary concerns. The part that turns providers into generated source should be
  a pure function of its already-loaded inputs: no file access, no global state, no clock,
  no randomness. A pure core is the only practical way to get the **determinism** the
  contract demands and to test exhaustively without touching disk.

- **Make determinism a property of the design, not a patch.** The package loader does not
  promise an order for packages, files, or positions, and hash-map iteration is randomized.
  Decide *once* how output is ordered (anchor it to source position) and route every
  ordering decision through that. Then *prove* it (see the shuffle test below).

- **Lean on the language’s own type machinery.** You are emitting Go that must compile and
  be `gofmt`-clean. The Go standard library can render a type to source *and* tell you which
  packages it references in one pass; use it, and run the final text through the standard
  formatter. Let the tools own correctness of formatting and imports so your code owns
  correctness of *wiring*.

- **Model the domain so the wiring logic is uniform.** The provider kinds (function, method,
  variable, field, conversion, struct type, …) look different on the surface but reduce to
  the same thing: some input types, some output types, and a way to render the producing
  expression. Find the abstraction that lets the *ordering and signature inference* code
  ignore the kind.

- **Separate user errors from broken invariants.** User mistakes deserve located,
  actionable errors. Violations of your own internal invariants (states that valid input
  can never produce) deserve a loud crash at the point of violation, never a guessed
  fallback: an “impossible” switch case that quietly returns a zero value or a plausible
  default hides the bug and resurfaces later as a silent miscompile. Keep the two
  categories distinct, and make sure nothing in the second category is reachable from
  valid input. The fuzz target is how you earn that guarantee.

- **The central invariant is your acceptance test.** *Valid input produces compilable
  output, deterministically, idempotently.* Everything else is detail. When a design choice
  is unclear, ask which option makes that invariant easier to *guarantee* (not merely to
  satisfy on today’s examples), and take it.

- **Resist over-engineering.** This is a focused tool. Prefer a small number of clear types
  and direct code over layers of indirection. Add structure when a real edge case demands
  it, and let the test suite, not speculation, tell you where the edges are. Weigh
  slimming the same way, by total complexity: a change that removes code simplifies; one
  that adds subtle code to shave off a dependency or an option does not.

## Testing strategy

The behavior is broad and exact, so the test suite is where most of the engineering value
lands. The following techniques are strongly recommended; the reference implementation
relies on all of them.

### Table-driven tests over a fixture corpus

Most behavior is “given this small package of providers, produce this output (or this
error).” Drive that from a table: each entry names a fixture (a small, self-contained
providers package), the generation options, and whether it expects success or a specific
error. Adding a behavior or edge case becomes adding a fixture and a row, cheap enough that
you will actually cover the long tail (every provider kind, every coercion direction, every
rejection, the generics matrix, the collision cases). Give each fixture a one-line
description of what it exercises.

### Golden files for generated output

Generated source is large and every character matters, so assert it against **golden files**
rather than inline string literals. Gate regeneration behind an environment variable (e.g.
`UPDATE=1 go test`) so intentional changes are a quick regenerate-and-review-the-diff, while
CI compares only. For *error* cases, store the expected diagnostic text in a golden too, and
also assert the error wraps the right programmatic sentinel (so classification, not just
message text, is pinned). Keep fixture positions stable so an unrelated edit does not churn
every golden.

Underlying both: never assert with a loose substring match, on generated output or on
diagnostic text. A substring check passes by accident, and keeps passing when the message
it pinned changes with the old fragment still inside it, precisely the change it existed
to flag. Prefer, in order: a golden wherever the output is deterministic (it pins every
character, and an intended change is a cheap regenerate-and-review); a sentinel where
classification is the point and wording is incidental (it survives rewording without
loosening what it asserts); and, when a line worth pinning sits inside genuinely
nondeterministic output (a toolchain message carrying a temporary path, say), an exact
match of that whole line, still never a substring.

### Verify that generated output actually compiles

A golden match proves you produced the *expected* text; it does not prove the text
*compiles*. Type-check the generated output in the context of its package (overlay the
generated file onto the fixture and load the result). This makes “valid input ⇒ compilable
output” a tested guarantee. Do it in memory. You do **not** need to shell out to `go build`.
(A fixture that deliberately exercises best-effort on invalid input is the one exception, and
should be marked to skip the compile check.)

### Fuzz the central invariant: in both modes

Write a fuzz target that takes an arbitrary string, tries to load it as a Go package, skips
it if it is not valid Go, and otherwise runs generation. Assert two things: generation never
panics, and whenever it *succeeds*, the emitted code type-checks. Seed the corpus from your
fixtures. **Run it in same-package mode as well as separate-package mode.** Same-package
generation, where the generated file shares a namespace with existing declarations, is
exactly where collision bugs hide, and a separate-package-only fuzzer will never reach them.

### Prove determinism by shuffling

Determinism is a contractual property, so test it directly: generate once for a reference,
then regenerate many times over **shuffled** package and file orders (and re-randomized map
iteration) and assert each result is byte-identical: both the generated **source** and the
`-v` **report**. For error fixtures, assert the **diagnostic** is identically stable under
shuffling (its position and any tie-break selection). Use fixtures with providers spread
across several files and packages so the test has something to get wrong.

### Do not use the real package loader in unit tests

The real Go package loader is slow (it can spawn the toolchain and touch the filesystem) and
non-hermetic. For unit/component tests, load fixtures from an **in-memory source filesystem**
instead: type-check the fixture’s source against the host toolchain’s export data for the
standard library (so `io`, `os`, `sql`, etc. resolve) without any subprocess or disk access.
Use it for the table-driven tests, the golden tests, the compile checks, the fuzzer, and the
determinism test. Reserve the **real** loader for a small number of end-to-end tests that
deliberately exercise the loader-and-flags boundary (pattern resolution, the actual CLI,
writing a file, and the stale-output / tolerated-error classification), kept separate from
the fast unit tests.

### Test the I/O boundary on its own

Because the core is pure, test the boundary separately: flag/destination resolution
(including the “ambiguous when more than one package is scanned”, “required for a separate
package”, and import-path validity rules), the classification of load errors into fatal vs.
tolerable, and error reporting through the configured streams.

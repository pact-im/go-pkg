# A plumb tutorial

plumb generates the function that wires your constructors together. You tag each
constructor with a `//plumb:<name>` comment; plumb reads its parameters and
results and writes a function named `<name>` that calls the constructors in
dependency order.

Unlike [wire](https://go.dev/blog/wire), you don’t write that function or
declare its signature; plumb infers it from the constructors. This tutorial
builds a small greeter to show how.

The finished program is in this directory; the steps below build up to it. Run
the commands from here.

## The pieces

The program has three types. A `Message` is the text to show. A `Greeter` holds
a Message and greets with it. An `Event` runs a Greeter. Each has a constructor:

```go
type Message string

func NewMessage() Message { return Message("Hi there!") }

type Greeter struct{ Message Message }

func NewGreeter(m Message) Greeter { return Greeter{Message: m} }

type Event struct{ Greeter Greeter }

func NewEvent(g Greeter) Event { return Event{Greeter: g} }
```

(`Greeter.Greet` and `Event.Start` are ordinary methods; see [greeter.go](greeter.go).)

To build an `Event`, you call the constructors in order, threading each result
into the next:

```go
func main() {
	message := NewMessage()
	greeter := NewGreeter(message)
	event := NewEvent(greeter)
	event.Start()
}
```

Three lines of plumbing for three constructors. The list grows with every new
dependency, and every caller that wants an `Event` writes it again. plumb writes
it for you.

## Generating the wiring

Add a `//plumb:build` comment to each constructor. `build` is the name of the
function plumb will generate:

```go
//plumb:build
func NewMessage() Message { return Message("Hi there!") }

//plumb:build
func NewGreeter(m Message) Greeter { return Greeter{Message: m} }

//plumb:build
func NewEvent(g Greeter) Event { return Event{Greeter: g} }
```

Then run plumb:

```
go generate ./...     # runs //go:generate plumb -output=plumb_gen.go
```

It writes `plumb_gen.go`:

```go
// Code generated by plumb. DO NOT EDIT.

package main

func build() (event Event) {
	message := NewMessage()
	greeter := NewGreeter(message)
	event2 := NewEvent(greeter)
	event = event2
	return
}
```

That’s the wiring you wrote by hand, generated. `build` takes nothing and returns
an `Event`, and plumb worked both out from the set. Every type a constructor needs
is produced by another constructor, so there are no parameters. The `Event` is
produced but never consumed, so it’s the result. `main` shrinks to:

```go
func main() {
	build().Start()
}
```

## Errors thread automatically

Suppose a Greeter can be grumpy, and a grumpy greeter cancels the event. `NewEvent`
now returns an error:

```go
type Greeter struct {
	Message Message
	Grumpy  bool
}

//plumb:build
func NewGreeter(m Message) Greeter {
	return Greeter{Message: m, Grumpy: rand.IntN(2) == 0}
}

//plumb:build
func NewEvent(g Greeter) (Event, error) {
	if g.Grumpy {
		return Event{}, errors.New("the greeter is grumpy; no event today")
	}
	return Event{Greeter: g}, nil
}
```

Regenerate, and `build` grows an error. It’s checked right after the call that
can fail and returned immediately:

```go
func build() (event Event, err error) {
	message := NewMessage()
	greeter := NewGreeter(message)
	event2, e := NewEvent(greeter)
	if e != nil {
		err = e
		return
	}
	event = event2
	return
}
```

You didn’t edit a signature anywhere. You added an error to one constructor and
re-ran plumb. (With wire, you’d also have to update the injector’s declared
return type.) `main` handles it:

```go
func main() {
	event, err := build()
	if err != nil {
		fmt.Println("no event today:", err)
		return
	}
	event.Start()
}
```

Run it a few times; about half the time the greeter is grumpy and the event is
cancelled.

## Unprovided types become inputs

So far `build` takes no arguments, because every input has a producer. Let the
greeting text come from outside instead. `NewMessage` takes a `Phrase`, and nothing
in the set produces one.

```go
type Phrase string

//plumb:build
func NewMessage(phrase Phrase) Message { return Message(phrase) }
```

Regenerate. A `Phrase` is required but unproduced, so plumb makes it a parameter:

```go
func build(phrase Phrase) (event Event, err error) {
	message := NewMessage(phrase)
	greeter := NewGreeter(message)
	event2, e := NewEvent(greeter)
	if e != nil {
		err = e
		return
	}
	event = event2
	return
}
```

That’s the rule in both directions: a type produced but not consumed is a result,
and a type consumed but not produced is a parameter. `main` supplies the Phrase:

```go
func main() {
	phrase := Phrase("Hi there!")
	if len(os.Args) > 1 {
		phrase = Phrase(os.Args[1])
	}
	event, err := build(phrase)
	if err != nil {
		fmt.Println("no event today:", err)
		return
	}
	event.Start()
}
```

```
go run . "Welcome!"
```

This is the finished program in this directory.

## Seeing what plumb inferred

`plumb -v` prints a report to stderr: the packages it scanned, and for each set,
every provider’s inputs and outputs along with the signature it inferred for
`build` (the `inject` line).

```
plumb: scanned 1 package(s): go.pact.im/x/plumb/_tutorial
plumb: generating into package "go.pact.im/x/plumb/_tutorial"

set "build" (3 providers, 3 instantiations):
  func NewMessage in(Phrase) → out(val Message)
  func NewGreeter in(Message) → out(val Greeter)
  func NewEvent in(Greeter) → out(val Event, err error)
  inject build in(Phrase) → out(val Event, err error)
```

## What’s next

That’s the whole idea: tag constructors, and plumb writes the wiring, inferring
the signature from what the providers need and produce. From here:

- Constructors aren’t the only providers. plumb also wires struct fields, package
  variables and constants, interface bindings, methods, and generic providers.
- A constructor that returns a `func()` is treated as a cleanup. plumb collects
  the cleanups into one teardown that runs in reverse order, unwinding a partial
  build if a later provider fails.

See `go doc go.pact.im/x/plumb` for the full reference.
